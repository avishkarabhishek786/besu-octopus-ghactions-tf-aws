## 1. What Stage 9 adds
A **fully-private Blockscout block explorer** for the Besu chain, plus the
**dedicated `explorer-rpc` pool** it indexes from. No public exposure; reached via
`kubectl port-forward` from the in-VPC runner (or SSM). Operator/observability
tooling — it sits next to the monitoring stack, not in the app VPC.

## 2. The decisive choice — in-cluster, with a dedicated DEBUG/TRACE RPC pool
Blockscout's indexer needs **`debug`/`trace`** to surface **internal
transactions** — access that ETH/NET/WEB3 (the SWIFT + app-rpc edges) deliberately
do **not** expose. Three considerations drove the design:

- **In-cluster (chosen) vs separate app-VPC.** Blockscout is operator tooling
  (like Grafana), not an external app-consumer. Hosting it in-cluster lets it
  reach a **ClusterIP-only** RPC with `debug`/`trace` that **never crosses an
  external edge**. The app-VPC + PrivateLink pattern (Stage 8) would force trace
  access over an edge — rejected.
- **Dedicated `explorer-rpc` pool (chosen) vs reusing a validator's opsRpc.**
  Reusing opsRpc would over-privilege Blockscout (QBFT/ADMIN/TXPOOL) and put
  indexing load on a validator. A dedicated pool is least-privilege
  (ETH,NET,WEB3,DEBUG,TRACE only), isolates indexing load, and mirrors the
  established per-pool node machinery.
- **Why DEBUG and TRACE.** Besu serves both `debug_` and `trace_` namespaces on
  one HTTP listener; Blockscout's `besu` variant uses them for internal-tx and
  block tracing. WS (`eth_subscribe`) gives realtime head updates.

So: a separate Besu RPC node pool, **ClusterIP only, no TLS, no JWT, no edge** —
trust is the in-cluster network boundary (only Blockscout + the runner reach it).

## 3. Database — bundled in-cluster Postgres
Postgres StatefulSet on a gp3 PVC, bundled in the chart (decision: not RDS).
Blockscout's DB is **re-indexable from the chain**, so a single non-HA replica is
fine; the mirror rule keeps the *same* component in prod, only larger (tfvars
`blockscout_pg_storage_size_gib`: 10 non-prod / 50 prod).

## 4. Fully private / no egress (preserved stance)
Blockscout by default calls external price/market/token/sourcify APIs. ALL of
that is disabled (`DISABLE_EXCHANGE_RATES`, `SOURCIFY_INTEGRATION_ENABLED=false`,
`DISABLE_KNOWN_TOKENS`, `SUPPORTED_CHAINS=[]`, …) so the explorer makes **no
external calls** — consistent with the project's "nothing public" rule. Secrets
(DB password + Phoenix `SECRET_KEY_BASE`) are generated by Terraform
(`random_password`); the human provides nothing.

## 5. Wiring map (BUILT)
- **`besu-node` chart** — `role=explorer-rpc` (HTTP+WS, `ETH,NET,WEB3,DEBUG,TRACE`,
  ClusterIP service, no TLS/JWT); `peers.explorerRpc` joins static-nodes + the
  node allowlist.
- **`besu-genesis` chart** — `explorerRpcCount` key-gen + `explorerRpc` pubkeys in
  `node-pubkeys.json` + `besu-node-explorer-rpc-*` secret writes.
- **`modules/secrets`** — explorer-rpc node-key containers + output.
- **`modules/besu`** — `besu-explorer-rpc-1..E` releases, peering, genesis
  count/prefix, `explorerRpc` values, and outputs `explorer_rpc_http_url` /
  `explorer_rpc_ws_url` (in-cluster ClusterIP DNS) for the explorer.
- **`helm/charts/besu-blockscout`** (new) — Postgres StatefulSet + Service,
  Blockscout backend Deployment + Service, a Secret (TF-provided), NOTES.
- **`modules/blockscout`** (new) — `random_password` (db + secret_key_base) + the
  gated `helm_release`, consuming the besu module's explorer-rpc URLs.
- **root** — `module "blockscout"` gated by `deploy_in_cluster_resources &&
  enable_blockscout && explorer_rpc_count>0`; vars + `blockscout_portforward_command`
  output. tfvars enable it in BOTH envs (mirror rule).

## 6. Deploy prerequisites + order (when the human budgets a deploy)
**Prerequisite:** the Terraform **state bucket was deleted** between sessions —
re-create it (the state-bucket bootstrap, described in `claude-code-setup.md` in the frozen `besu-aws` reference repo) before any apply.
Then, on top of the Stage-8 chain deploy flow:
1. Chain apply (laptop) with `explorer_rpc_count=1` → the explorer-rpc secret
   container + topology come up.
2. In-cluster apply from the **in-VPC runner** (`deploy_in_cluster_resources=true`)
   → genesis writes the explorer-rpc key; the explorer-rpc pod + Blockscout +
   Postgres deploy. Blockscout runs migrations then indexes.
3. Reach the UI: `terraform output blockscout_portforward_command` →
   `kubectl -n besu port-forward svc/blockscout 4000:4000`, open localhost:4000.
4. Same-day teardown (sweep the Postgres PVC EBS too).

## 6a. UI (frontend + proxy) — BUILT (2026-06-26, branch blockscout-ui)
The prod deploy-test (2026-06-23) confirmed the backend is **API-only** (`/` → 404):
modern Blockscout split the UI into a separate `blockscout/frontend` container.
Added to the chart:
- **backend `ghcr.io/blockscout/blockscout:9.0.2`** (API-only). NOTE: an earlier
  draft pinned `blockscout/blockscout:11.2.1` from the GitHub *repo* release page —
  that tag does NOT exist as an image. **Image tags ≠ repo release tags:** Docker
  Hub `blockscout/blockscout` is stale (~7.0.2 max) and the real images live on
  **ghcr.io**, where the backend tops out at 9.0.x. Resolve from
  `https://ghcr.io/v2/blockscout/blockscout/tags/list` (token via
  `ghcr.io/token?scope=repository:blockscout/blockscout:pull`). 9.0.2 == `:latest`
  on 2026-06-26.
- **`frontend` Deployment+Service** — `ghcr.io/blockscout/frontend:v2.3.5` (ghcr
  `frontend` tops out at v2.3.x; the repo's v2.8.x release tags are NOT images —
  same lesson as the backend). Separate version track, runtime-configured via
  `NEXT_PUBLIC_*` (host, protocol, ws, network name/id from chain values;
  stats/visualizer omitted = no egress). v2.3.5 == `:latest` on 2026-06-26.
- **nginx single-origin `proxy`** (ConfigMap+Deployment+Service) — routing:
  `/api`,`/socket`,… → backend:4000, `/` → frontend:3000. **This is the one
  port-forward target.**
- **`blockscout_access_host`** (root var, default `localhost:4000`) bakes
  `NEXT_PUBLIC_API_HOST`/`APP_HOST` so the browser hits the proxy's origin (no
  CORS). The port-forward local port MUST match it.
helm lint + template + `terraform validate` pass.

## 7. Live-run findings (RESOLVED 2026-06-26 non-prod deploy-test)
The UI build was deployed end-to-end in non-prod and verified (then torn down
same-day). What the live run resolved — and the chart fixes it produced:
- **Image tags.** The biggest gotcha (see §6a): repo release tags ≠ image tags.
  Final verified pins: backend **9.0.2**, frontend **v2.3.5**, both on ghcr.io.
- **Migration.** The eval task `Elixir.Explorer.ReleaseTasks.create_and_migrate()`
  is **valid on 9.0.2** — backend migrated cleanly on first start and indexed
  ("Index already caught up"). No rename needed for this image.
- **Readiness probe FIXED.** `/api/v1/health` returns **HTTP 400** on 9.0.2 (the
  health path changed across majors), so the httpGet probe never passed and the
  pod sat at 0/1 while the API served fine. Chart now uses a **TCP** readiness
  probe on :4000 (version-stable). Don't reintroduce the httpGet health probe
  without re-confirming the path on the pinned image.
- **Deployment strategy FIXED.** A rolling update briefly ran two backend pods
  against the same Postgres → migration-lock conflict → new pod CrashLoopBackOff.
  Chart now sets `strategy: Recreate` on the backend Deployment.
- **Frontend through the proxy works.** Proxy `/` → HTTP 200 (Next.js UI);
  `/api/v2/blocks`, `/api/v2/stats`, `/api/v2/main-page/blocks` → live chain data.
  Single origin (`NEXT_PUBLIC_API_HOST=access_host`) over one port-forward — no
  CORS/SSR issues observed.
- **Besu variant / trace.** Blockscout's `besu` variant indexed blocks via the
  explorer-rpc pool. `txpool`/`pending_transaction` logs a cosmetic
  `-32604 Method not enabled` (explorer-rpc omits TXPOOL by design) — non-fatal.
- **Resources.** The 2-node non-prod cluster was oversubscribed (backend +
  kube-prometheus-stack); scaled the nodegroup to 3 to schedule everything. Tune
  `blockscout.resources` / node count if pods stay Pending.
- **Seed tx.** Offline-signed a nonce-0 zero-value self-transfer from the admin
  EOA (broadcast via explorer-rpc `eth_sendRawTransaction`) so the UI shows tx
  views; Blockscout indexed it (`result: success`).

## 7b. Optional microservices — stats + visualizer (added 2026-06-26, chart v0.2.x)
Verified live in the prod deploy-test. Two OPTIONAL Blockscout microservices,
both `enabled: true` by default in the chart, both ClusterIP + fully private (no
external egress):
- **stats** (`ghcr.io/blockscout/stats:v2.16.0`) — homepage + Stats-page charts.
  Creates its OWN `stats` database in the bundled Postgres (`STATS__CREATE_DATABASE`)
  and reads the indexed `blockscout` DB + backend API. Serves JSON on :8050.
- **visualizer** (`ghcr.io/blockscout/visualizer:v0.2.1`) — Sol2UML diagram on a
  verified contract's page. Stateless, no DB, no egress. Serves on :8050.
- **Frontend wiring:** `NEXT_PUBLIC_STATS_API_HOST` / `NEXT_PUBLIC_VISUALIZE_API_HOST`
  (chart values `frontend.statsApiHost` / `visualizeApiHost`). These are
  BROWSER-side (NEXT_PUBLIC) → each microservice needs its OWN port-forward
  (defaults `localhost:4001` stats, `localhost:4002` visualizer) IN ADDITION to
  the proxy on `:4000`. CORS is enabled (`*`) on both so the browser at
  `localhost:4000` can call the other ports.
- **Postgres fix (REQUIRED for stats):** the backend pool alone exhausts the
  default `max_connections=100` → stats fails with `FATAL: too many clients
  already` / `pool timed out`. The chart now passes `-c max_connections=200`
  (value `postgres.maxConnections`) and raises the PG memory limit to 2Gi.
- **Image-tag caveat** (same as backend/frontend): these are **ghcr.io** tags
  resolved from `/v2/blockscout/<svc>/tags/list`, NOT GitHub repo release tags.
- **NOT enabled:** Write functions / WalletConnect — deliberately omitted (the
  "no browser wallet, server-side signer" decision, CLAUDE.md §1/§8.3). Enabling
  it would need an external WalletConnect project + browser-reachable RPC + the
  signer address allowlisted. sig-provider also omitted (needs external 4byte
  egress; verified contracts already decode via their ABI).
